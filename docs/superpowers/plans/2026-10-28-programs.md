# Programs (Sub-project 4a) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the `programs` module, which installs the user's programs after a clean install. The programs come from:
- a curated catalog;
- free winget ids;
- a `winget export` file from the old PC;
- direct installers, verified by SHA-256.

It also adds the commands `programs list`, `programs search` and `programs export`.

**Architecture:** System adapters live in `FormatKit.Core.SystemAccess` and join `ServiceSet`:
- the extended `WingetClient`;
- `DirectInstaller` and `HttpDownloader`;
- `UserContextRunner`.

A new project, `FormatKit.Programs`, holds:
- the embedded catalog;
- profile options and import parsing;
- item selection;
- one engine step per catalog category, plus `programs.other` and `programs.direct`.

The CLI registers the module after `drivers` and `cleanup`, and adds a `programs` command group.

**Tech Stack:** C# / .NET 10 (`net10.0-windows`), System.Text.Json, System.Net.Http (in-box), System.Security.Cryptography (SHA-256, in-box), System.CommandLine 2.0.14, xunit.v3, Serilog.

**Spec:** `docs/superpowers/specs/2026-10-28-programs-design.md`

## Global Constraints

- **Platform:** target `net10.0-windows` with nullable on and `TreatWarningsAsErrors`. Add no new NuGet packages.
- **Language and localization:**
  - Code, identifiers, comments, logs and repository docs are in English.
  - Every user-facing string goes in both `Resources/Strings.resx` (en) and `Resources/Strings.pt-BR.resx`, read through the project's `Localization/Strings` class.
- **References:** `FormatKit.Programs` references only `FormatKit.Core`.
- **No localized text parsing:** never parse localized tool text. Parse only:
  - exit codes;
  - numbers;
  - the JSON that `winget export` writes;
  - text that the plan's own PowerShell snippet prints.

  `programs search` is the only exception: it passes winget's text through, unparsed, for a human to read.
- **Command-line safety:**
  - Every winget id, version or source passed on a command line must match `^[A-Za-z0-9._+-]+$`; adapters throw `ArgumentException` otherwise.
  - Direct-installer arguments are passed as an argument list, never through a shell.
- **Tests:**
  - Tests use fakes for every system abstraction.
  - Tests that touch the real machine or the network carry `[Trait("Category", "Integration")]`.
- **Exit codes:** they come from `FormatKit.Cli.ExitCodes`; add no new codes.
- **Commits:** commit after each task. Messages end with the Co-Authored-By trailer of the model that wrote the code.
- **Unit suite:** run with `dotnet test -- --filter-not-trait "Category=Integration"`.

## Rulings against the spec (made while planning)

- **P1:** an item with `context: user` fails, with the next action "sign in and run again", when no interactive user is signed in (spec 6 now says the same; an earlier draft deferred it to the resume run at logon).
  - Why: the engine records each step once and never re-runs a finished step. In practice FormatKit always runs inside a signed-in session, either from the CLI or from the resume task at logon.
- **P2:** resume after a crash re-runs the whole step.
  - Winget items do not reinstall, because `winget list` reports them as installed.
  - Direct items are recorded after success in `%ProgramData%\FormatKit\programs-direct.json`, keyed by `name|sha256-or-path`, and skipped when the key is present.
  - This replaces spec 6's "recorded in the run state", which the engine does not support per item.

## Review Focus

1. **Winget not registered yet on a fresh install.** The first winget item tries to register App Installer once. If winget is still missing, every winget item fails with the App Installer next action, and direct items still run. Pinned in Task 6.
2. **An installer that hangs despite `--silent`.** The install timeout (`Timeouts.Install`, 30 min) ends that item as failed with a timeout message, and the next item runs. Pinned in Task 1 (`TimedOut` maps to `Failed`) and Task 6.
3. **An `importFile` from another winget version.** Extra or missing optional properties are tolerated. `PackageIdentifier` values that fail the safe pattern are skipped with a warning, not a profile error. Pinned in Task 5.
4. **A large download on a slow link.** The download has its own timeout (`Timeouts.Download`, 30 min). A partial file is deleted, and the item fails without running anything. Pinned in Task 2.
5. **The same program listed twice** (catalog plus `winget` plus import) installs once. The first occurrence wins, in the order catalog → winget → import. Pinned in Task 5.

### Task 2: Direct installer and downloader

**Files:**
- Create: `src/FormatKit.Core/SystemAccess/IHttpDownloader.cs`, `HttpDownloader.cs`, `DirectInstaller.cs`

**Interfaces:**
- Produces:
  - `public interface IHttpDownloader { Task DownloadAsync(Uri url, string destination, TimeSpan timeout, CancellationToken ct); }`. It throws `IOException` / `HttpRequestException` / `TimeoutException` on failure and deletes a partial file before throwing.
  - `HttpDownloader`: a single static `HttpClient`, https only (throws `ArgumentException` for any other scheme), streams to `destination + ".part"` and renames on success.
  - `AppPaths.DownloadsDirectory => Root\downloads` and `AppPaths.ProgramsDirectFile => Root\programs-direct.json`.
  - `public enum DirectStatus { Installed, RebootRequired, HashMismatch, DownloadFailed, Failed }`.
  - `public sealed record DirectResult(DirectStatus Status, int ExitCode, string Message)`.
  - `public sealed record DirectSource(string Name, Uri? Url, string? LocalPath, string? Sha256, IReadOnlyList<string> Args)`.
  - `public class DirectInstaller(IHttpDownloader downloader, IProcessRunner runner, IFileSystem files, AppPaths paths)` with `Task<DirectResult> InstallAsync(DirectSource source, CancellationToken ct)`.
  - `IFileSystem` gains `Stream OpenRead(string path)`, used to hash the file. Implement it in `FileSystem` and in `InMemoryFileSystem`.

Behaviour:
1. **Download.** For a URL, download to `DownloadsDirectory\<first 16 hex of SHA-256(url)><extension from the URL path>`.
2. **Verify.** Compute the SHA-256 when `Sha256` is set and compare case-insensitively.
   - On a mismatch, delete the download (never the local `LocalPath`) and return `HashMismatch`. Nothing runs.
3. **Run.**
   - `.msi`: `msiexec.exe /i <file> /qn /norestart`.
   - `.exe`: `<file>` with `Args`.
   - Any other extension: `ArgumentException`. The profile validation in Task 5 prevents this case.
   - Use `Timeouts.Install`.
4. **Map the exit code.**
   - `0` → `Installed`.
   - `3010` or `1641` → `RebootRequired`.
   - `TimedOut` or any other code → `Failed`, with the code in the message.
5. **Clean up.** Delete the download after `Installed` or `RebootRequired`. Keep it after `Failed`.

Winget step behaviour (spec 6, ruling P1):
- **CheckAsync** returns true only when every program is already installed and `upgrade` is false. Any exception in CheckAsync → false.
- **ExecuteAsync:**
  1. First `IsAvailableAsync`. If winget is missing, run `powershell.exe -NoProfile -NonInteractive -Command "Add-AppxPackage -RegisterByFamilyName -MainPackage Microsoft.DesktopAppInstaller_8wekyb3d8bbwe"` once, then check again.
     - If it is still missing, every item fails and the step returns `Fail(NextAction_WingetMissing, …)`.
  2. Then, per program:
     - If it is installed and `upgrade` is off → AlreadyInstalled.
     - If it is installed and `upgrade` is on → `UpgradeAsync`.
     - If it is not installed → `InstallAsync`.
     - `Context == User`:
       - When `!UserSession.HasInteractiveUser`, the item fails with `Item_Failed_NoUser`.
       - Otherwise the same winget arguments run through `IUserContextRunner`, and the exit code is mapped with the same table. Expose the mapping from Task 1 as `WingetClient.MapExitCode(int code, bool upgrade, bool timedOut)`.
     - Each item's outcome becomes one message line, `"<name>: <localized status>"`.
     - Exceptions per item (not cancellation) become a Failed line.
     - Cancellation is checked between items, never during one.
  3. The step result:
     - any Failed → `Fail(NextAction_SeeLog)`;
     - otherwise any RebootRequired → `Reboot`;
     - otherwise `Success`.

     The messages list holds every line either way.

Direct step behaviour:
- Per entry:
  - if `DirectProgress.IsDone(key)` → AlreadyInstalled;
  - otherwise `DirectInstaller.InstallAsync`, then `MarkDone` on Installed or RebootRequired.
- The status maps to the strings above.
- The same aggregation rules apply.
- CheckAsync is true when every key is done.
